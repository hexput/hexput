# AGENTS.md

This file provides guidance to AI coding agents (Claude Code and others) working with code in this repository. `CLAUDE.md` in this same directory is a symlink to this file — edit this file, not that one.

**Keep this file current.** As the project moves past planning and into implementation, update the Project Status section (and anything else below that's gone stale) to reflect what's actually true — don't let this drift into a description of a project that no longer exists.

## Language

The maintainer (Erdem) is Turkish. **Talk to him in Turkish; write everything else in English.**

- **Conversation** — Turkish. Chat replies, questions, explanations, status updates.
- **Everything written down** — English. Code, comments, doc comments, commit messages, PR descriptions, specs, planning artifacts, CI config, and this file.

The split is deliberate: the repository stays readable to any contributor or agent regardless of language, while day-to-day discussion happens in the maintainer's own. Do not "helpfully" switch a document to Turkish, and do not answer in English because the surrounding files are English.

BMAD mirrors this — `_bmad/custom/config.user.toml` pins `communication_language = "Turkish"` while `document_output_language` stays `English`. Note that `_bmad/config.toml`, `_bmad/config.user.toml` and `_bmad/*/config.yaml` are installer-generated and overwritten on every install; `_bmad/custom/` is the only durable place to change this.

## Project Status

_Last updated: 2026-10-22._

**Epic 1 is code-complete: Stories 1.1–1.10 are all implemented.** The Cargo workspace has 23 crates under `crates/`. `hexput-lexer` tokenizes source; `hexput-shared::diagnostics` defines shared errors and stable codes; `hexput-ast` holds owned, spanned syntax in flat expression and block arenas; `hexput-parser::parse` parses the whole Epic 1 grammar (expressions, declarations, assignments, member access, blocks, conditionals, loops, functions, calls, objects, arrays). `hexput-interpreter::evaluate` now runs the **whole language** on an explicit continuation stack — no host recursion from input nesting, iteration count, or call depth: values, §4 operators and conversions, optional access, §7 absent-data/reference rules, block scoping, `let`, assignment, `if`/`else`, `while`, `for … in`, `break`/`continue`, named and anonymous functions, closures (captured by reference), calls, and `return`. Call depth is bounded by the documented `hexput_interpreter::CALL_DEPTH_LIMIT` (1024). A function cannot be the Script result (`type.function_result`), as a function has no wire representation. `hexput-shared::diagnostics` also owns the one terminal rendering — `render_diagnostic(&Diagnostic, &str, RenderOptions)` returns the approved three-line form (location line, source line, caret marker) as a `String`, with no colour, no I/O and no dependencies; `Diagnostic` carries a `Severity` (`Error`/`Warning`) for Story 1.10's findings, and `hexput-ast` re-exports all of it so the parser and interpreter reach it without a forbidden `hexput-shared` edge. `hexput_interpreter::evaluate_with_variables` is the second entry point: it binds caller-supplied **starting variables** into the root scope before the top-level named functions hoist, with `Array::from_values`/`Object::from_entries` for building collection inputs from outside the crate. `hexput-cli-core` implements `hexput eval <script> [--var name=<expression>]…` over it — `clap` parses the arguments, a `--var` value is an ordinary Hexput expression, the result prints in Hexput literal form (pasteable back into a script) and the exit contract is `0` success / `2` usage / `1` everything else, with every failure rendered to stderr by `render_diagnostic`, and stdout carrying a successful evaluation's result (or explicitly requested help/version text). A supplied `--var` name that the Script's own top level also declares is `syntax.duplicate_declaration`, never a silently discarded value. `run`/`run_with` return a `std::process::ExitCode` and write through sinks, so the whole CLI is tested in-process; `hexput-bin`'s `hexput.rs` is nothing but `args_os()` and the hand-off. `hexput-check::check(&Program, &Environment, &Policy) -> Findings` is the static check pass (FR-26, AD-8): one pure function over a parsed AST, depending on `hexput-ast` **alone** — the `hexput-shared` edge it was scaffolded with is gone, and `check-crate-graph.py` now pins the set. It reports undeclared reads and assignments, argument counts against functions the Script declares, literal-operand type errors, unreachable code, unused locals, calls to names outside a supplied callable list, and uses of a construct `Policy` disables (the six FR-3 toggles, all defaulting to enabled). Two contracts govern it: **a finding is never a false positive** — where a rule would need a value, the pass stays silent — and **a missing callable-name list is not an empty one**, the first suppressing the unknown-call finding entirely and the second meaning "nothing but local functions is callable". Duplicate `let` and loop control outside a loop are the *parser's* findings and can never reach a parsed AST, so the pass documents that instead of carrying dead code; a test pins the parser's rejection. Severity follows one line: certain-to-fail is an error, cannot-fail (unused local, unreachable code) is a warning, which makes "a warning can never reject a Script" true by construction. `hexput check <script> [--var name] [--callable name]…` drives it — `--var` takes a **name alone** because a static check needs the name and never the value — writing a one-line summary to stdout, findings to stderr through Story 1.8's renderer, and exiting `1` only for an error-severity finding. `Code::ALL` enumerates every diagnostic code so `tests/shared.rs` can assert coverage rather than trusting a hand-maintained list. Tests live in `hexput-tests`. This is a from-scratch v2 rewrite; there is no v1 code in this repository.

**Epic 2 is code-complete: Stories 2.1–2.8 are all implemented.** `hexput-config` parses the System Config TOML file into a typed `SystemConfig` (`[transport.uds|tcp|websocket]`, `log_level` default `info`, `session_ttl_secs` default `300`; unknown keys rejected; at least one transport required) and `resolve(flag, env, default_path) -> Result<Loaded, ConfigError>` applies AD-7's precedence — `--config`, then `HEXPUT_CONFIG`, then `/etc/hexput/config.toml` (`%ProgramData%\hexput\config.toml` on Windows) — **never falling through** from a source that names a missing file. The env value and default path are parameters so tests never touch the process environment. Every `ConfigError` names the path, its source and the problem (with line/column where there is one). `crates/hexput-config/config.example.toml` documents every field and a test parses it. `hexput-daemon`'s `run`/`run_with` mirror `hexput-cli-core` (exit `0`/`2` usage/`1` failure, sinks, `hexput-bin` only hands off `args_os()`); on success they log the resolved path and source through a plain `tracing-subscriber` `fmt` subscriber at `log_level`, then wait on a caller-supplied shutdown future (SIGINT/SIGTERM in the real binary). Story 2.2 lands the wire protocol, sans-IO. `hexput-shared::wire` defines `CorrelationId(u64)`, the `#[non_exhaustive]` PascalCase `MessageType` (`Init`, `ExecutionStart`, `Result`, `Error`) and `Envelope<P>` — on the wire a MessagePack map of exactly `id`/`type`/`payload`, encoded with field names, `id` nil only on an `Error` response whose request id was unreadable. `hexput-shared::ids::ClientId` is 128 bits spelled as 32 lowercase hex characters (Display/FromStr/serde); `hexput-session` generates it. `hexput-port` (depends on `hexput-shared` alone, pinned by the graph check) is the codec every adapter wraps: `FrameDecoder` (push bytes, pull frames; 4-byte big-endian length prefix; `MAX_FRAME_LEN` 16 MiB; an oversized prefix poisons it), `encode_frame`, `decode(&[u8]) -> Result<Envelope<Value>, ProtocolFailure>` and `encode`, over `rmpv::Value` (re-exported). Every failure is one `ProtocolCode` (`protocol.malformed_frame`/`truncated_frame`/`invalid_envelope`/`unknown_message_type`/`frame_too_large`), echoing the request id whenever it is readable; `protocol` is a wire-only category, never a §7 `Category`. `ErrorBody` is the single error payload, built from a `Diagnostic` (with span) or a `ProtocolError`; `error_response` wraps it. Nesting is bounded by `MAX_NESTING_DEPTH` (128). Story 2.3 makes the daemon listen. `hexput-port` now also defines the `Port` trait an adapter implements — `split()` into an `Inbound` half (`recv() -> Received::{Message, Malformed, Closed}`) and an `Outbound` half (`send(Envelope)`), native `async fn`-in-trait with `Send` futures, still no async runtime in the crate — so a connection can be read and written independently. `hexput-transport::uds` (Unix only) is the first adapter: `UdsListener::bind(path, mode)` removes a stale socket nobody listens on, refuses a live socket or any non-socket file without touching it, applies an optional `mode` by binding inside a private `0700` directory beside the path, `chmod`-ing, then `hard_link`-ing onto the path (so no other user connects before the mode holds, and nothing that appeared at the path is replaced), and `close()` removes the file only if it is still its own. `hexput-connection::serve<P: Port>(port, Arc<Sessions>)` is the transport-generic core loop (tested with an in-memory Port, no socket); a malformed frame gets its protocol error and reading continues unless it was fatal. `hexput-daemon` binds before logging "daemon started" (bind failure → exit `1` naming the path), runs each connection as its own task in a `JoinSet`, and removes the socket on shutdown; a System Config naming `[transport.tcp]`/`[transport.websocket]` exits `1`, since no adapter serves them until Epic 5. System Config's `[transport.uds]` gained the optional `mode` (three or four octal digits as a string, at most `"0777"`). The Spine gained the `hexput-connection → hexput-port` edge (dated amendment), and `check-crate-graph.py` pins `hexput-transport`, `hexput-connection` and `hexput-daemon`'s exact sets. Stories 2.4 + 2.5 (built as one spec) complete the init handshake. `hexput-session` is the Session registry: `Sessions` over a `DashMap<ClientId, Session>`, where a `Session` holds the single live copy of the Backend's `Config` (AD-5; empty until Epic 3 defines keys, so any `config` key is refused), its `RegisteredFunction`s and a *set* of attached `ConnectionId`s (a crate-local `u64` counter, not a wire id). `InitRequest::from_value` decodes an `Init` payload by hand — exactly `config` (a map) and `registrations` (an array of `{name: <non-empty string>}`, no duplicates); absent or nil is missing, both missing keys are named together, `registrations: []` is valid (empty is not missing). `Sessions::create` issues a Client ID from the OS CSPRNG (`getrandom`; a collision draws again) with the creating Connection attached; `attach` exists for reconnect (Epic 5); `detach` removes the last attachment and the Session together under the shard lock (`remove_if_mut`), then calls the one private `teardown` — never `Drop` — which Story 5.8 will delay behind a TTL. `serve` answers a valid `Init` with `Result {client_id: "<32 hex>"}`, an invalid one with `protocol.invalid_payload` (no Session), a second `Init` with `protocol.already_initialized`; the init gate is one check (`ExecutionStart` before init → `protocol.init_not_completed`); a Backend's `Result`/`Error` → `protocol.unexpected_message`. However a connection ends, `serve` detaches it on its one exit path. `hexput-daemon` owns one `Arc<Sessions>` per run; aborted connection tasks on shutdown drop it with the run. `check-crate-graph.py` pins `hexput-session` to `hexput-port`/`hexput-shared`/`hexput-globalvar`. Story 2.6 serves Direct Execution. `hexput_exec::execute(&Program, Vec<(Arc<str>, Value)>)` is the one Executor entry point (AD-3) — today a pass-through to `evaluate_with_variables`, which Epic 3 wraps with enforcement; it is the only Daemon-side caller of the interpreter's `evaluate*` (the CLI's local `hexput eval` is not a Daemon path). `hexput-interpreter` re-exports `Program` for it, and `Array`/`Object` gained borrowed `iter()`s. `is_identifier` moved from `hexput-cli-core` into `hexput-parser` (public), so the CLI and the Daemon share one judgement. `hexput_script::direct_execution(&Value) -> Result<Value, Box<ErrorBody>>` decodes an `ExecutionStart` payload by hand — exactly `source` (string) and `variables` (map; `{}` is valid, absent/nil is missing, both missing named together), each name a §2 identifier appearing once — converts every value losslessly or refuses it as `protocol.invalid_payload` naming the path (`variables.user.tags[2]`; integers outside ±2^53, NaN/infinity, binary, ext, non-string or repeated keys, invalid UTF-8), parses with no cache, runs through the Executor, and answers `{value}` (a whole number within ±2^53 as a MessagePack integer, `-0` as `0`, anything else float64; key order kept) or the parser/interpreter `Diagnostic` as an `ErrorBody`. Before converting, an iterative walk refuses a result nested past `MAX_RESULT_DEPTH` (`MAX_NESTING_DEPTH - 2`) as `protocol.result_too_deep` and one certain to exceed `MAX_FRAME_LEN` (a lower bound that also stops shared-collection blow-up early) as `protocol.response_too_large`. `hexput-connection` routes an initialized `ExecutionStart` there and replaces a reply the adapter cannot frame with `protocol.response_too_large` carrying the id. `protocol.not_implemented` is gone. The Spine gained `script --> port` and `conn --> script` (dated amendment); `check-crate-graph.py` pins `hexput-script` and `hexput-exec`; moving `is_identifier` dropped `hexput-cli-core`'s now-unused `hexput-lexer` edge. Story 2.7 takes Direct Execution out of the connection's loop (AD-6, FR-16): every initialized `ExecutionStart` is its own task in the connection's `JoinSet`, run through `spawn_blocking` so runtime workers never run Script code. The loop `select!`s the (cancel-safe) `Inbound::recv` against `join_next`, stays the one writer of the `Outbound` half (no lock, a send always driven to completion), and writes each reply with its id as that execution finishes — completion order, not submission order; `Init`, refusals and malformed-frame answers stay inline. Any number of executions may be in flight per connection. When the peer stops sending (clean close or fatal frame) the connection stops reading, waits for its executions, writes their replies, then detaches; a lost stream or failed write abandons them at once (dropping the `JoinSet`). A panicked execution task is logged at `error` and the connection keeps serving. `hexput-connection` gained a `tokio` dependency (external; no workspace edge). Story 2.8 traces every request back to its Client ID (FR-12). `Sessions::connect()` issues a `ConnectionId` when a connection opens, before init — `create(init, connection)` and `attach(client_id, connection) -> bool` take it rather than issuing one — so one id names a Connection for the whole run. `serve` runs each connection in a `connection` span (`connection = <id>`, `client_id = none` until init — marked, never omitted) and each request in a child `request` span (`id`), both created at `ERROR` level so no `log_level` disables them; the request span is carried onto the `spawn_blocking` thread and re-entered to write the reply. On init the connection span is *replaced* by one carrying the Client ID (recording into the old one would omit or duplicate the field); "init completed" is its first event. No message interpolates a Client ID; refusals now log `refused a request` with their `code` at `debug`, and the Daemon's "connection accepted" became `serve`'s "connection opened". System Config gained `log_format = "text" | "json"` (default `text`, validated like `log_level`); JSON is `tracing-subscriber`'s `json` feature (Spine Stack amendment) with the current span and the span list, so span fields are JSON fields. `serde_json` is pinned for the tests that parse those lines. `tracing` caches callsite interest process-wide, so `tests/connection.rs` runs every `serve` under a discarding subscriber — a callsite first hit with none can be cached as disabled while another test installs its own.

**Epic 3 is code-complete: Stories 3.1–3.13 are all implemented** (host calls, their capability grants, all six Resource Budget dimensions, the language feature toggles and the static check mode, tunable per Session and per execution and updatable at runtime, Value Secrets, Registered Methods, and modifications flowing both ways by Reference ID; this paragraph supersedes the Epic 2 notes above where they differ). A call whose callee is a bare name no scope declares is a **host call**; a local binding shadows it, and naming one without calling it stays `reference.undeclared_identifier`. The interpreter is resumable: its frames address the AST by index (`ExprId`/`BlockId`/statement position) instead of `&'p` references, and `Machine<P: Deref<Target = Program>>` holds either `&Program` (`evaluate*`, unchanged signatures) or `Arc<Program>` (`hexput_interpreter::Execution`, `Send + 'static`). `Execution::run(self) -> Outcome::{Finished, HostCall, Paused, OutOfMemory, AllocationsExceeded}`; a `HostCall` carries the name, the detached `Argument`s (value + span) and the call span, and `resume(&Value)` hands the execution back. A function or cyclic argument is `type.function_argument`/`type.cyclic_argument` on that argument; `evaluate*` (and so `hexput eval`) refuse every host call as `capability.unknown_function`. `hexput_exec::execute(Arc<Program>, variables, Host)` is now `async`: every segment runs on the blocking pool, and between segments it measures arguments (the argument depth limit, default `ARGUMENT_DEPTH_LIMIT` 12 → `depth.argument_too_deep`; arguments certain to exceed a frame → `host.function_failed`), asks `hexput_enforce::Capabilities::check_call` (unregistered → `capability.unknown_function`), then awaits `hexput_rpc::Caller::dispatch_authorized` (renamed from `call` in Story 3.2) holding no thread. A Backend `Error` or a malformed reply is `host.function_failed`, a connection that ends first `host.no_reply` (new §7 category `Category::Host`), both spanned on the call. The wire↔value conversion moved from `hexput-script` to `hexput_exec::wire` (`to_hexput`, `to_wire`, `measure`, `check_result`). `hexput-rpc` owns correlation: `Calls` (per-connection id counter, pending table of `oneshot`s, `issue`/`complete`/`unsendable`/`close`) and the cloneable `Caller`; the wire gained `MessageType::Call` with payload `{name, arguments, execution}` (`execution` — the originating `ExecutionStart`'s id, set via `Caller::for_execution` — added after Story 3.3), answered by `Result {value}` (exactly that key) or `Error` (its string `message` carried into the Script error). `hexput_script::direct_execution(payload, registrations, caller)` is `async` and runs decode/parse/result conversion on the blocking pool. `hexput-connection` spawns each execution as an ordinary task (`JoinSet::spawn`, instrumented with its request span), passes the Session's registrations read once per execution, selects on the call queue as a third branch, writes each `Call` as the single writer (an unframable `Call` fails only that call), routes a Backend `Result`/`Error` whose id names a pending call back to it (otherwise `protocol.unexpected_message` as before), logs a Backend `Error` at `debug`, and `close()`s the table the moment it stops reading so pending and later calls fail with `host.no_reply` at once. `check-crate-graph.py` pins `hexput-rpc` = {`hexput-port`}, `hexput-enforce` = {`hexput-shared`}, and adds `hexput-rpc` to `hexput-connection`'s set. Story 3.2 adds the blanket grant: an `Init` registration is `{name, blanket}`, `blanket` an optional boolean (absent = no grant; anything but a boolean → `protocol.invalid_payload` naming `registrations[i].blanket`), carried by `RegisteredFunction::blanket()`; `Sessions::registrations(client_id)` (replacing `registration_names`) returns them per execution, never cached. `hexput-connection` hands `(name, blanket)` pairs through `hexput-script` to `Host::new`, and `hexput_enforce::Capabilities::check_call` alone decides: a blanket-granted name proceeds with no round trip; an unregistered one is refused. Story 3.3 adds the per-call handler: for a name registered without a blanket grant `check_call` returns `Decision::AskHandler(Question)`, `hexput-exec` asks the Backend with a separate `Authorize {name, arguments}` message (`MessageType::Authorize`, built and correlated by `hexput-rpc` under the same per-connection id counter as `Call`, via `Caller::ask_authorization`) before any `Call`, waits at most the authorization timeout (default `hexput_exec::AUTHORIZATION_TIMEOUT`, 5 s; holding no thread or lock; a later answer is consumed by the table and dropped), and hands a `HandlerAnswer` to `Question::decide` — only `Result {value: true}` proceeds, and the answer is never cached. Every denial is the very same `capability.unknown_function` as an unregistered name. The `Refusal` carries a `Reason` (`unregistered`/`refused`/`handler_invalid`/`handler_failed`/`handler_timeout`/`handler_no_reply`) that `hexput-exec` logs at `debug` (`function`, `reason`, "refused a host call") from the execution's async task — so the event carries the request span — and never shows the Script. A runtime running Scripts that may ask needs timers enabled (the Daemon's does). `hexput-exec` gained an external `tracing` dependency. `check-crate-graph.py` also asserts `RESTRICTED_NAMES`: `dispatch_authorized` and `ask_authorization` may appear in no production crate but `hexput-exec` and `hexput-rpc`, and `MessageType::Call`/`MessageType::Authorize` in none but `hexput-rpc`, `hexput-shared` and `hexput-port` (AD-3; `hexput-tests` exempt). Story 3.4 enumerates the rest: `hexput_interpreter::BUILTINS` is the one list of builtin names — empty (no standard library, §11) — and `Execution::root_names()` lets a test assert that a fresh execution binds only its starting variables and top-level functions; a sweep of ambient spellings (`fs`, `process`, `globalThis`, …) is `reference.undeclared_identifier` when read and `capability.unknown_function` when called, with nothing sent. Story 3.5 bounds CPU time and memory. `hexput-shared::budget::Dimension` is the six-dimension `#[non_exhaustive]` enum (`ALL`, `as_str`); `budget.cpu_time_exceeded` and `budget.memory_exceeded` are in `Code::ALL`. The interpreter only meters: `Execution::metered(Meter { slice, memory_ceiling })` makes `run` stop with `Outcome::Paused` (resumable via `Paused::resume`, spanned on the running construct) after a slice of work — one unit per step plus one per 256 string bytes read or written — and with `Outcome::OutOfMemory` (heap already dropped) once the heap's approximate live bytes pass the ceiling: slot footprints charged on allocation/growth and credited on release, plus strings as a metered `Text` that credits its own charge when its last handle drops (so a shared string counts once); a concatenation whose result alone would cross the ceiling stops before allocating. `evaluate*` run unmetered. `hexput_enforce::Budget` owns the limits (defaults `DEFAULT_CPU_TIME` 1 s, `DEFAULT_MEMORY` 64 MiB), `charge_cpu(elapsed, span)` and `memory_exceeded(span)`, each refusal an `Exceeded {dimension, diagnostic}`. `hexput-exec` creates one `Budget` per execution, runs each blocking segment as a loop of `SLICE` (10 000-unit) slices timed with `Instant`, charges between slices, at a host call before anything is sent and when the Script finishes (so the limit is a hard bound), also times its own blocking work for the Script (binding variables, converting arguments and replies), never times a wait on the Backend, and logs a stop at `debug` (`dimension`, "stopped an execution over its budget") from the execution's task. A runaway therefore ends about 1 s in and frees its blocking thread, so Daemon shutdown no longer hangs on one; the tests' slow Scripts loop 50 000 turns to stay far inside that budget. Story 3.6 bounds the four counted dimensions, each its own `Limits` field, default constant (`DEFAULT_ALLOCATIONS` 1 000 000, `DEFAULT_RPC_CALLS` 100, `DEFAULT_OUTPUT_SIZE` 1 MiB, `DEFAULT_SIDE_EFFECTS` 100) and `Code::ALL` code (`budget.allocations_exceeded`/`rpc_calls_exceeded`/`output_size_exceeded`/`side_effects_exceeded`). **Allocations** are defined by the language (LANGUAGE-REFERENCE §7), not by Rust: each string literal evaluated, concatenation, to-string conversion of a concatenation's non-string operand, `for … in` key and array/object literal, plus each append taking a collection's length past a power of two (1→2, 2→3, 4→5, 8→9 — the heap counts these in `array_store`/`object_store`); starting variables and host-call values (built by `Heap::attach`) never count. The interpreter counts (`Execution::allocations()`) and stops at `Meter::allocation_ceiling` with `Outcome::AllocationsExceeded` (heap already dropped). `Budget::charge_rpc_call(span)` charges one RPC call and one side effect at every `Outcome::HostCall` whose arguments can be sent — after the slice's CPU charge and the argument checks, before the capability decision (a call with an unsendable argument is not counted), so a refused/denied/failed call counts and an `Authorize` question is part of its call — refusing the call that would cross either (RPC checked first) before anything is sent. Output size is the exact MessagePack length of the `{value}` payload (never Story 3.10's `findings`), computed without encoding by `hexput_exec::wire::payload_size` (an iterative walk that stops once past `min(limit, MAX_FRAME_LEN)`, pinned against `rmp_serde`) and charged by `Budget::charge_output` when the Script finishes (after its last CPU charge), spanned on the whole Script; `hexput-script` keeps only the frame/depth protocol checks. `Limits` has `with_*` builders and `Budget::with_limits`; `hexput_exec::execute_with_limits` (re-exporting `Limits`) runs under explicit limits. Story 3.7 makes every limit tunable. `hexput-shared::budget::Setting` is the one table of the eight settings — each `path()` (`budget.cpu_time_ms`, `budget.memory_bytes`, `budget.allocations`, `budget.rpc_calls`, `budget.output_size_bytes`, `budget.side_effects`, `argument_depth`, `authorization_timeout_ms`), inclusive `min()`/`max()` (the Daemon's ceiling; zero only for the counted dimensions; output at most `MAX_FRAME_LEN`, asserted at compile time in `hexput-port`) and `default()`, from which `hexput-enforce`'s `DEFAULT_*` constants are derived. `Settings` (private `Option<u64>`s; built only through the validating `set`, which returns `OutOfRange`; `get`, `effective`, `overlay`) holds some of them. `hexput_port::decode_settings(value, prefix)` is the one decoder, used for `Init.config` (prefix `config`) and the new optional `ExecutionStart.overrides` (prefix `overrides`; absent or nil sets nothing): nested maps of MessagePack integers, a float (even whole), a negative or out-of-range value, a wrong type, an unknown/dotted/repeated/non-string key all refused naming the full backticked path and, for a value, the range (`` `config.budget.rpc_calls` must be an integer from 0 to 100000; found 200000 ``) — never clamped; a refused `Init` creates no Session, a refused `ExecutionStart` runs nothing. `hexput-session`'s `Config` now holds `Settings` (`Config::settings()`; `config: {}` is valid, any other key refused), and `Sessions::for_execution(client_id)` reads registrations and settings together under one lock (`Sessions::settings` alone too); `hexput-connection` calls it once per execution. `hexput_script::direct_execution(payload, registrations, settings, caller)` overlays the overrides on the Session's settings — changing nothing stored — and calls `execute_with_limits(…, Limits::from_settings(&effective))`. `Limits` gained `argument_depth` and `authorization_timeout` (`DEFAULT_ARGUMENT_DEPTH`, `DEFAULT_AUTHORIZATION_TIMEOUT`; `hexput_exec::ARGUMENT_DEPTH_LIMIT`/`AUTHORIZATION_TIMEOUT` remain as aliases of those defaults), which `hexput-exec` applies, and a depth error names the limit in force. No crate edge changed. Story 3.8 makes the Config updatable without reconnecting: a Backend request `ConfigUpdate {config}` (`MessageType::ConfigUpdate`, behind the init gate) carries a *complete* Config in `Init.config`'s shape, decoded by `hexput_session::Config::from_update_payload` through the same `decode_settings` (payload exactly `{config}`; absent/nil is missing, an unknown or repeated key refused). It **replaces, never patches** — a setting it leaves out is back to the Daemon default, `config: {}` resets all. `Sessions::update_config(client_id, Config) -> bool` swaps the single live copy under the shard lock; `hexput-connection` handles it inline like `Init`, answering `Result {}` (an empty map) and logging "config updated" at `debug`, or `protocol.invalid_payload` with the stored Config untouched. One binary message is one envelope, no length prefix (`decode`, so a bad one is a non-fatal `Malformed`); a text message is `protocol.malformed_frame` ("a WebSocket text message; Hexput frames are binary messages", not fatal); Ping/Pong never surface; an over-limit message is a fatal `protocol.frame_too_large`; a peer's Close is driven until tungstenite has flushed its reply, then `Closed(None)`; a TCP end without a Close frame (`ResetWithoutClosingHandshake`, `UnexpectedEof`) is `Closed(None)`; anything else `Closed(Some(_))` (invalid UTF-8 text and peer protocol violations fail the connection, RFC 6455); after that, always `Closed(None)`. Unlike a byte stream, a WebSocket ends both directions together: a reply still owed after the peer's Close, or after a TCP end with a TLS `close_notify`, cannot be sent (tungstenite refuses the write), which the module doc states, a test pins and deferred-work records; an end without `close_notify` leaves the writer usable. `send` writes one binary message and flushes; an encoding over `MAX_FRAME_LEN` is `InvalidInput`, nothing written. The halves come from `futures_util::StreamExt::split`. The Daemon sends no Close frame of its own (no `Port` close hook; deferred-work records it with `close_notify`). System Config: `[transport.websocket]` now requires `tls_cert`/`tls_key` (serde's missing-field error with its position; `WebSocketTransport.tls` is `Tls`, no longer optional) and its `bind` may be a bare IP, listening on `hexput_config::DEFAULT_WEBSOCKET_PORT` (7478). ## Build, Lint, Test

Run from the repository root. These are exactly the CI steps, in order — CI adds `--locked` to catch `Cargo.lock` drift, so use it locally too.

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
python3 scripts/check-crate-graph.py
cargo build --workspace --all-targets --locked
cargo test --workspace --locked
```

The cache benchmark (Story 4.4) is not a CI step beyond its quick mode, which `cargo test --workspace` already runs (locally on a disk-scarce machine, `cargo test --workspace --locked --release`, so only the release tree is built). Measure with `cargo bench -p hexput-tests --bench cache` (the `bench` profile builds like `release`; a positional filter such as `-- warm` runs one figure and skips the steady state and engine sections, `-- engine` runs only the in-process engine section with its budget-overhead line and writes no report); a quick check is `cargo test -p hexput-tests --bench cache --release`. Since Story 4.5 every run also measures the Rhai comparator (`rhai_compare/*`, Rhai's steady state and the side-by-side table), and since Story 5.9 the remote path: `remote_path/tcp_tls_cold_first_run` and `remote_path/tcp_tls_warm_cache_hit`, a TCP+TLS steady state and a UDS-vs-TCP+TLS transport table, all over loopback `127.0.0.1` on the same machine (the TCP and TLS stack cost, not network latency; `-- remote_path` runs only those two figures and writes no report). A full run writes its conditions (each leg's transport and topology under `workload.legs`), the three steady states (`steady_state`, `tcp_tls_steady_state`, `rhai_steady_state`, never merged) and the engine figures to `target/hexput-bench/cache-win.json` (under `CARGO_TARGET_DIR` when set) and compares the next run on the same machine against it; Criterion keeps its own history in `target/criterion/`.

`scripts/check-crate-graph.py` is the one non-obvious step. **A forbidden dependency edge does not fail `cargo build` while the crates are stubs** — nothing imports it yet, so the manifest edge resolves fine and clippy stays silent. The script asserts the AD-enforcing edges against the resolved graph from `cargo metadata`, which is what actually keeps AD-1/AD-3/AD-4/AD-5/AD-8 enforced rather than merely documented. If you add a crate or an edge, update it in the same change.

`scripts/check-windows.sh` (not a CI step) cross-lints the whole workspace for `x86_64-pc-windows-msvc` with `-D warnings`, so `cfg(windows)` code (the Named Pipe adapter and its tests) is checked on a non-Windows machine. It needs `rustup target add x86_64-pc-windows-msvc`, `clang-cl` and `llvm-lib`, and passes extra arguments to `cargo clippy` (`scripts/check-windows.sh --release`). It compiles only; the Windows tests run in CI's `windows` job.

NFR2's memory-safety rule is a workspace lint (`undocumented_unsafe_blocks = "deny"` in `[workspace.lints.clippy]`, inherited by every crate via `[lints] workspace = true`). The four crates NFR2 names — `hexput-lexer`, `hexput-parser`, `hexput-interpreter`, `hexput-exec` — escalate it to `#![forbid(...)]`, which an inner `#[allow]` cannot override. Any `unsafe` block needs a `SAFETY:` comment.

## Where tests go

Tests live in **`crates/hexput-tests`**, one `tests/<crate>.rs` per crate under test. Add a crate to that manifest's `[dev-dependencies]` as it gains code worth testing.

Two things about this are load-bearing:

- **Crates under test are dev-dependencies, never normal ones.** `check-crate-graph.py` enforces the Spine's rules over normal dependencies only, because those rules are about what *production* code can reach. That is what lets one test crate reach `hexput-enforce` (AD-3) or `hexput-transport` (AD-1) without weakening them — a normal dependency there fails the graph check, as it should.
- **These are integration tests.** A separate crate sees only the public API. A test that needs a private item has to stay in a `#[cfg(test)] mod tests` inside its own crate — that is the exception, and worth a comment saying why.

## What Hexput Is

A standalone scripting runtime daemon (Rust) — installed and run like Redis, not embedded like a library. Backend applications connect over a socket (Unix Domain Socket, Named Pipe, TCP+TLS, or WebSocket) and either run stateless scripts (one-shot or cached execution) or register stateful **Plugins** (persistent, event-driven, capability-sandboxed code units). No OS-level sandboxing — the language itself is the trust boundary, permanently, by design (see the brief's Risks section for why).

## Architecture (from the spine — treat the spine as authoritative, this is a summary)

**Paradigm:** Hexagonal (Ports & Adapters) at the transport boundary, wrapping an Actor-model runtime core.

**One crate per boundary, all under `crates/`.** These are Cargo dependency edges, not module conventions — a forbidden reach is a manifest the graph check rejects, not a review comment.

```text
# cross-cutting
hexput-shared        # diagnostics.rs, wire.rs, ids.rs, budget.rs, policy.rs — never a grab-bag

# language (no execution, no I/O, no host access)
hexput-ast           # AST node types + Span — data only
hexput-lexer         # tokenizer
hexput-parser        # parser — depends on lexer + ast
hexput-interpreter   # tree-walking evaluator — depends on ast only, no host reach
hexput-check         # static check (FR-26) — ast + shared ONLY, cannot execute (AD-8)
hexput-cli-core      # eval + check command logic

# daemon
hexput-transport     # UDS, Named Pipe, TCP+TLS, WebSocket adapters — one Port impl each
hexput-port          # wire envelope (MessagePack), request/response + event correlation
hexput-session       # Client ID -> Session, TTL, reconnect + credential validation
hexput-connection    # transient per-connection actor, attached to a Session (0..N per Session)
hexput-script        # Direct/Cached Execution: AST cache, parse/interpret
hexput-plugin        # Plugin actor: registration, event routing/ordering metadata
hexput-globalvar     # Global Variable store: concurrent per-Plugin map, independent of the actor's mailbox
hexput-exec          # the one shared Executor every execution mode funnels through
hexput-enforce       # Capability + Resource Budget enforcement — reachable ONLY via hexput-exec (AD-3)
hexput-rpc           # host-function registry, capability grants, outbound RPC (`Call`) to Backend and its correlation
hexput-config        # System Config (file) parsing — separate crate from per-backend Config (AD-5)
hexput-daemon        # wiring root: composes the above into run(SystemConfig)

# developer tooling
hexput-grammar       # tree-sitter grammar
hexput-lsp-core      # language server logic — lexer/parser/check only, never interpreter
hexput-playground    # loopback browser playground (FR-30) — a Backend over the wire protocol, embedded in the Daemon or standalone
hexput-tests         # every crate's tests, one tests/<crate>.rs per crate under test

hexput-bin           # the ONLY crate producing binaries: src/bin/{hexput-daemon,hexput,hexput-lsp}.rs
```

Read the spine's "Crate dependency graph" subsection before adding any edge. Nothing not listed there is permitted.

**Invariants that bind implementation** (full rationale in the spine; these are the ones a change is most likely to violate):

- Every Transport is an adapter into one `Port`; Core never branches on transport type (AD-1). Health/metrics ride the same `Port`, pre-init-gate.
- A Session may have zero or more concurrently attached Connections — never exactly one; no cross-Connection broadcast, each request/response stays with the Connection that issued it (AD-2).
- Direct Execution, Cached Execution, and Plugin Event handlers all call one `Executor` entry point — no path checks capability or consumes budget independently, including for the full duration of an `async = true` handler (AD-3).
- A Plugin's Global Variable store lives independently of its actor's mailbox; `hexput-session` is the only caller of its `teardown()`, invoked before the actor drops, never implied by `Drop` (AD-4).
- `hexput-session` holds the single live copy of per-backend Config; nothing else snapshots it (AD-5).
- Every execution dispatches as an independent async task; the only permitted serialization is a Plugin's own opted-in `priority` ordering among its own handlers for one Event (AD-6).
- System Config discovery (CLI flag > env var > default path) is identical regardless of packaging (AD-7).
- No lock is ever held across an `.await` point.

**Domain vocabulary** (use these terms verbatim in code — see PRD §3 Glossary for full definitions): `Daemon`, `Backend`, `Session`, `Connection`, `Client ID`, `Config` (per-backend, never a file) vs. `System Config` (file-based, daemon-operational), `Registered Function`, `Registered Method`, `Value Secret`, `Reference ID`, `Capability`, `Script`, `Direct Execution`, `Cached Execution`, `AST Cache`, `Resource Budget`, `Plugin`, `Event`, `Global Variable`, `Global Variable Locking` (concurrency strategy) vs. `Global Variable Behavior` (lifetime strategy: `forever`/`ttl`/`separate_each_trigger`/`keyed`).

**Stack** (pinned versions in the spine's Stack table — verify current before bumping): Rust 1.98.1 (2024 edition), Tokio, `tokio-tungstenite`, `rustls`, `serde`/`rmp-serde` (MessagePack wire format), `dashmap`, `moka` (AST cache), `criterion` (benchmarking), `rhai` (the bench's comparator, `hexput-tests` dev-only), `tracing`, `clap` (every CLI's arguments), `toml` (System Config), `tracing-subscriber` (the daemon's log output), `getrandom` (the OS CSPRNG behind Client IDs). `[workspace.dependencies]` pins feature sets with versions; members write `workspace = true` only.

**Deliberately out of scope** — don't reintroduce without checking the brief/PRD first: OS-level sandboxing (permanent, not deferred), transactional/rollback RPC effects, master-slave horizontal scaling (future work, not precluded by the design).
