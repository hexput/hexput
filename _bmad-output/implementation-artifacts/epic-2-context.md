# Epic 2 Context: Run a script over a socket

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Turn the Epic 1 language into a running daemon. An operator starts it from one System Config file. A Backend connects over a Unix Domain Socket, sends its per-backend Config and function registrations in a single init handshake, submits a one-shot script, and gets back the result or a structured error. No per-backend config file exists anywhere. This epic also sets up the structure every later epic builds on: the `Port` boundary that every transport adapts into, the Session/Connection split that reconnect and Plugins rely on, the single shared `Executor` that every execution mode goes through, independent async dispatch per execution, and `tracing` tagged with the Client ID, which operability work builds on.

## Stories

- Story 2.1: Start the daemon from a System Config file
- Story 2.2: Frame requests and responses on the wire
- Story 2.3: Accept connections over a Unix Domain Socket
- Story 2.4: Complete the init handshake with inline config and registrations
- Story 2.5: Attach connections to a session that outlives them
- Story 2.6: Run a one-shot script and get the result back
- Story 2.7: Keep slow executions from blocking anything else
- Story 2.8: Trace every request back to its Client ID

## Requirements & Constraints

- **System Config** is a file and holds only the daemon's operational settings: transport bind addresses and ports, TLS certificate paths, log level, and the default Session TTL. Its location is resolved by one fixed precedence: CLI flag, then environment variable, then a fixed default OS path. The precedence is the same under systemd, Docker, or anything else; packaging only sets the env var or mounts the default path. A missing file, a malformed file, or a missing required field makes the daemon exit non-zero with an error naming the file and the problem. The daemon never falls back to an undocumented default for a required field. The resolved path is logged at startup.
- **Per-backend Config never touches disk** and never configures the daemon. Changing it never reads, writes, or reloads System Config.
- **Init handshake:** a fresh connection sends Config and function registrations together in one init message. The daemon creates a Session keyed by a newly issued Client ID, stores both on it, and returns the Client ID. An init missing either part is rejected with an error naming what is missing, and no Session is created. Any execution request before init completes is rejected with a defined "init not completed" error, and nothing runs. Design the gate so that health/metrics can later be exempted from it; health/metrics themselves belong to a later epic.
- **Direct Execution** parses and evaluates a script with caller-supplied starting variables and returns the result on the connection that sent the request. It creates no AST Cache entry. A parse or runtime failure comes back as a protocol error response carrying the Epic 1 structured diagnostic (category, code, severity, message, span).
- **Reliability:** a malformed, truncated, or unknown-type frame gets a defined protocol error response. It never causes a panic or a silent drop. A failing script or a client that disconnects abruptly must not affect the daemon or any other connection's in-flight work.
- **Concurrency:** a slow execution never delays a fast one, on the same connection or a different one, and message processing continues throughout. One connection may have several executions in flight at once.
- **Logging:** every event emitted while handling a request carries the Client ID as a structured `tracing` span field, not as text in the message. Events before init still identify the connection and explicitly mark "no Client ID" instead of leaving the field out. The subscriber honours System Config's log level, and structured JSON output is available as a configured option.
- **Out of scope for this epic:** TCP+TLS, WebSocket, Named Pipe, reconnect and its credential, the Session TTL countdown, capability enforcement and Resource Budgets, runtime Config updates and per-execution overrides, the static-check mode, Cached Execution, Plugins, and health/metrics.

## Technical Decisions

- **Hexagonal core (AD-1):** every transport is an adapter that implements one internal `Port`. The core never imports a transport type or branches on one. Only `hexput-daemon` depends on `hexput-transport`, and `hexput-transport` depends on `hexput-port` alone. The UDS adapter creates the socket at the configured path and removes a stale socket file left by an unclean shutdown.
- **Connection drives the Port (amended 2026-09-23):** `hexput-connection` depends on both `hexput-session` and `hexput-port`. It reads envelopes and writes responses through the `Port` trait directly, not through a re-export from session. This edge gives no transport reach.
- **Wire format:** one MessagePack envelope carrying a correlation id, a message type, and a payload. Responses are matched to requests by correlation id and may arrive in any order. The envelope, the Client ID representation, and the error shapes are each defined once and reused by every later adapter; no adapter declares its own. Decoding has two phases (amended 2026-09-23). First, `rmp-serde` turns the bytes into an untyped `rmpv::Value`; its nesting limit bounds recursion. Second, the envelope is validated by hand, so each failure gets its exact `protocol.*` code and the correlation id is recovered whenever it can be read. Later stories convert payloads to typed structs with `rmpv::ext::from_value`. The field layout beyond this is left to the implementation.
- **Session vs. Connection (AD-2):** a Session is its own entity, keyed by Client ID, holding Config and registrations. It has zero or more attached Connections, and its type must not encode "exactly one". Each Connection attaches to at most one Session and holds no state that outlives it. A response goes only to the Connection that issued the request; siblings get nothing. In this epic, a Session is torn down when its last Connection detaches. Teardown goes through one explicit path, never through `Drop`, so that the Epic 5 TTL work can delay that same path without moving it.
- **Client IDs are unguessable (amended 2026-09-23):** `hexput-session` draws each Client ID's 128 bits from the OS CSPRNG via `getrandom`. A Daemon that cannot read the CSPRNG issues no Client ID. The Epic 5 reconnect secret will reuse this source. The Session registry is a `dashmap` keyed by Client ID.
- **Config ownership (AD-5):** `hexput-session` holds the single live copy of a Session's Config. Nothing else takes a snapshot of it; readers go through that copy on every dispatch. `hexput-config` (System Config) and `hexput-session` do not depend on each other.
- **One Executor (AD-3):** every execution path reaches script evaluation through one `Executor` entry point in `hexput-exec`, with no second path around it. Capability and budget enforcement will later sit behind it (`hexput-enforce` is reachable only through `hexput-exec`), so scripts must not be evaluated from anywhere else. `hexput-script` owns Direct Execution and depends on the parser, the interpreter, `hexput-check`, and `hexput-exec`. Once the check mode exists, `hexput-script` is the one place that invokes the check on Direct Execution, and it reads the mode from the live Config.
- **Non-blocking dispatch (AD-6):** each execution runs as an independent async task on the shared Tokio runtime. No per-connection serial queue exists anywhere in the path. No lock of any kind is held across an `.await`.
- **Crate edges are compiler-enforced:** follow the spine's crate dependency graph exactly, including its dated amendments. Any new edge updates `scripts/check-crate-graph.py` in the same change; the script pins exact dependency sets. Daemon crates stay `lib`. `hexput-bin`'s `hexput-daemon.rs` is a thin `main()` that only hands off to `hexput-daemon`, whose `run` returns an exit code instead of exiting. The daemon's `--config` flag uses `clap`, like every other CLI.
- **Pinned stack, feature sets included:** tokio 1.53.1, serde 1.0.229, rmp-serde 1.3.1, rmpv 1.3.1 (`with-serde`), dashmap 6.2.1, getrandom 0.4.3 (no features), tracing 0.1.44, clap 4.6.7 (`derive`), toml 1.1.6 (`std`/`parse`/`serde`, no serializer, since System Config has no write API), and tracing-subscriber 0.3.23 (`fmt`/`std`). Story 2.8 adds JSON output as a feature of that same tracing-subscriber pin. `[workspace.dependencies]` pins each version together with its feature set, and members write only `workspace = true`, so no two crates can disagree about what a dependency provides.
- **Glossary names are used verbatim** in code: `Daemon`, `Backend`, `Session`, `Connection`, `Client ID`, `Config` vs. `System Config`, `Registered Function`, `Direct Execution`.
- **Result values:** a Script result cannot be or contain a function or a cycle; the interpreter already rejects these. Results and starting variables cross the wire as data only.

## Cross-Story Dependencies

- 2.1 (System Config) and 2.2 (envelope and Port) come first, and 2.3's UDS adapter needs both. The 2.4 handshake needs 2.2 and 2.3. 2.5's Session/Connection model is where 2.4 creates Sessions, so the two are built together. 2.6 needs an initialized connection from 2.4/2.5. 2.7 hardens 2.6's dispatch. 2.8 threads the Client ID through all of them and uses 2.1's log level.
- From Epic 1, this epic uses the parser, the interpreter (`evaluate_with_variables` for starting variables), and the shared `Diagnostic` shape for error responses.
- Later epics build on this one. Epic 3 adds enforcement, budgets, Config keys and Config updates behind the same `Executor` and the same live Config copy. Epic 4 adds Cached Execution to `hexput-script`. Epic 5 adds three more adapters behind the same `Port`, adds reconnect (reusing the CSPRNG source), and puts the TTL delay on 2.5's teardown path. Epic 7 builds health/metrics and FR-12 logging on 2.2's Port and 2.8's tracing.
