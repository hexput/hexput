- (decision) Major new capability added post-finalize: a second registration mode, Plugin Registration, alongside the existing stateless Direct/Cached Execution mode (§4.2). A Plugin is source containing a 'plugin { name = ..., ... }' backend-defined metadata block, top-level Global Variable declarations (persistent, shared state -- deliberately contrasts with FR-5's 'no state bleed' guarantee for stateless Cached Execution, which stays true for that mode only), and one or more handler functions annotated @Event(<name>). Example syntax supplied by user, captured verbatim in addendum.
- (decision) Plugin lifecycle: state persists for the lifetime of the Backend's Client ID -- survives reconnect (since Client ID already carries state per FR-2), torn down on disconnect-without-reconnect or explicit unregister. Event names are Backend-defined free strings (like Registered Functions), except BackendRegisteredInit which is a reserved lifecycle event invoked once at registration before the plugin accepts other events. Global Variable locking: default is per-top-level-key locking (DashMap-like -- mutating one key doesn't block sibling keys); Backend sets the default strategy (safe vs unsafe/lock-free) at registration time, AND may additionally allow Plugin code itself to override the strategy for a specific variable -- both configuration surfaces confirmed by user (not either/or).

- (decision) OQ-8 resolved: handler ordering for handlers bound to the same event is controllable via @Event(<name>, priority = N), gated by whether the Backend's config permits Plugin-level ordering control. - (change) Course correction (2026-09-24, Erdem, during Story 3.1 planning; sprint-change-proposal-2026-09-24.md): two requirements added after final. **FR-27 Registered Methods** — `registerMethod(objKey, fn)` binds a Registered Function to an object key; a script calls it as `value.name(args)` on a value whose Value Secret carries that key; the call rides the same generic `Call` message as a plain Registered Function call, carrying the receiver itself; a registered method wins over an own property of the same name; an unregistered method name is the same capability denial as an unregistered function; argument/receiver nesting is capped by a Config limit, default 12. **FR-28 Value Secret** — every value crossing to the Backend carries hidden metadata (`__secret`: `ref` Reference ID, optional `key`, further Backend-defined fields — modelled as `ValueHolder { key: Option<String>, ref: String, value, rest }`); the Backend reads and edits it, a script never can (reading yields `null`, writing is silently ignored, iteration skips it); a `Call` reply may report modifications by Reference ID, applied inside the execution so every binding holding that value observes them. Rationale (user): methods make host objects feel like objects in other languages, and Reference IDs let the Backend change the values it was handed without a second round trip. Also recorded Story 3.1's wire decision in FR-6: one generic `Call` message (not function-specific, since methods ride it too), and host-side failures as a `host` error distinct from capability denial. Glossary gained Registered Method, Value Secret, Reference ID; Config's glossary entry names the depth limit; MVP scope §6.1 lists both FRs. Four interpretive defaults were chosen by the agent and flagged for review in the proposal (Reference ID aliasing across copies, ref lifetime, modification report shape, method-over-property precedence).
- (decision) Same day, Erdem's answers to the four flagged defaults: (A3) a Reference ID names a location — a collection itself, or the variable/property/element a scalar or string arrived in — never a copy; the agent's A2 aliasing default was withdrawn. Modifications flow both ways: a script writing a referenced location is reported in the execution's `Result` `modifications` (example: Backend-supplied `n = 8`, `n = 9; return { ok: true };` → `modifications: [{ref, value: 9}]`). (B) ref source/lifetime and (C) the `[{ref, value}]` whole-value report shape accepted as proposed. (D2) a Registered Method wins over an own property and can never be overridden by a script (`capability.method_override`), reported by the static check and the language server where the target is provably keyed. FR-27/FR-28 consequences updated accordingly.
